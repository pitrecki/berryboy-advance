# Deterministic headless scenario captures

Build with JDK 21 and `mvn verify`. `tools/benchmark.py` requires Python 3 and
launches `berryboy.desktop.ScenarioRunner` from `target/classes`. Keep local ROMs,
BIOS, saves and configuration outside Git. The runner never downloads game data.

## Local configuration

Create an ignored `benchmarks/games.local.json`, mapping the five identifiers in
`suite.json` to local assets. Paths are relative to that configuration file:

```json
{
  "games": {
    "golden-sun": {
      "rom": "roms/golden-sun.gba",
      "rom_sha256": "REPLACE_WITH_SHA256",
      "bios": "roms/gba-bios.bin",
      "bios_sha256": "REPLACE_WITH_SHA256",
      "input": "roms/golden-sun-input.tsv",
      "input_sha256": "REPLACE_WITH_SHA256",
      "reference_video_sha256": "REPLACE_WITH_REFERENCE_RGB_STREAM_SHA256",
      "reference_audio_sha256": "REPLACE_WITH_REFERENCE_PCM_SHA256"
    }
  }
}
```

This example is incomplete: normal captures require all five configured games,
deterministic input and both references. Missing assets and checksum mismatches
fail before any game runs. Optional `save` also requires `save_sha256`; each
repetition gets its own copy, preserving the initial save. Optional `backup`
overrides detection: 0=SRAM, 1=Flash64, 2=Flash128, 3=EEPROM512, 4=EEPROM8K.
Use an explicit EEPROM type when loading an existing EEPROM save.

For direct `ScenarioRunner` properties, optional `initial_save_sha256` verifies
the existing `save` file before restoring cartridge bytes or running the guest.
A missing file, mismatched hash or absent `save` path fails the capture. Without
that property, a missing `save` file still starts a fresh cartridge backup.

Dirty backups are written to a temporary sibling file, forced to storage and
closed before an atomic replacement. Choose a save folder whose filesystem
supports atomic moves; unsupported replacement fails without a non-atomic retry.
Failures leave the in-memory backup dirty for retry. Temporary files are never
chosen as load sources. File force/rename alone does not qualify physical
power-loss durability.

Optional `devices` is a bit mask: RTC=1, solar=2, gyro=4, tilt=8, rumble=16.
Gyro cannot share pins with RTC/solar. Optional `rtc` is a deterministic ISO local
datetime, default `2000-01-01T00:00:00`; it advances from guest cycles.

An input recording contains strictly increasing guest-cycle timestamps:

```text
# cycle keys tiltX tiltY gyro solar
0       0    0x392 0x3a0 0x6c0 232
280896  1    0x392 0x3a0 0x6da 232
561792  0    0x392 0x3a0 0x6c0 232
```

Keys use the GBA button mask; sensor axes range 0–4095, solar threshold 0–255.
Events include warmup time. The BIOS, when supplied, must be exactly 16 KiB;
execution starts at its reset vector. Without BIOS, the direct-entry diagnostic
path is used and BIOS-dependent SWIs/IRQs fail explicitly. HLE is not provided.

## Running and interpreting results

```bash
python3 tools/benchmark.py --config benchmarks/games.local.json
```

The script follows `suite.json`: 30 seconds of guest warmup, 600 seconds of guest
measurement and three repetitions per game. Budgets round up to complete native
frames. Runs execute as fast as the headless host permits; the duration is guest
time, not a paced physical playback measurement. Use a new output directory for
each invocation (`--output` optionally supplies it).

`--smoke` instead runs three frames, without warmup, once per configured entry;
it permits a subset or an original synthetic ROM and does not require reference
captures. It reports `diagnostic`, never performance qualification.

Each repetition produces:

- `report.json`: asset/input/initial-save/final-backup hashes, backup type/size,
  save-write status, commit/dirty state, runtime/hardware,
  cycle/frame/sample counters, p50/p95/p99/max execution work and deadline misses.
- `frames.jsonl`: cycle/PC/CPSR checkpoints and the SHA-256 of each RGB888 frame.
- `first.png`, `last.png` and streamed stereo PCM16 `audio.wav` at 32768 Hz.
- Separate stdout/stderr logs and the exact scenario properties.

Capture hashing/PNG/WAV/trace IO runs on a dedicated host worker with a two-frame
queue. Submitted pixels and PCM are copied before emulation reuses the buffers.
Backpressure preserves order, and worker failures fail the run. Final reports
are written only after capture drains and joins. A 30-frame comparison against
the sequential capture path produced byte-identical traces, WAV and checkpoint
PNGs; this demonstrates output stability, not physical playback performance.

Video reference hashing concatenates each measured frame's pixels in row-major
RGB888 order. Audio reference hashing uses the measured interleaved signed
PCM16 stream in little-endian byte order, without the WAV header. References
must use the same assets, seed, inputs, warmup and frame budget. A reference
mismatch fails the run. A reference generated by this emulator establishes
replay stability only; independent captures are needed for hardware correctness.

The summary reports `captured-unqualified` for completed normal captures.
Headless work deadlines, guest-frame continuity and software audio-buffer counts
are distinct from physically presented frames, device underruns and audible
A/V drift. Physical counters are `null`, and Bold results remain `unrun`.
Average instruction throughput or a short successful capture cannot pass the
full acceptance gate in [BENCHMARKS.md](BENCHMARKS.md).

## Selected video checkpoints

For direct `ScenarioRunner` properties, set `checkpoints=1029,1272` to capture
named PNGs and raw video state in addition to the normal stream. IDs are absolute
one-based guest-frame IDs, must be unique and inside the measured interval, and
cannot select warmup frames. Invalid selections fail before creating output.
The owner copies state through read-only peeks, then the existing bounded worker
writes the independently owned snapshot. Normal RGB/PCM hashes do not change.
The diagnostic copy is outside the reported CPU execution-work interval; these
headless work timings still do not measure physical presentation.

For the matching mGBA capture, add `--checkpoints 1029,1272` to
`tools/reference_capture.py` using a newly compiled `tools/mgba-capture.c` binary.
The adapter uses raw reads without charging guest cycles. Checkpoint frame records
include `video_state_sha256`, and the reference report identifies RGB888 software
color-effect arithmetic. Example comparison:

```bash
python3 tools/compare_video_state.py \
  target/local-run/video-state-1029.bin \
  target/local-reference/video-state-1029.bin \
  --output target/local-video-state-comparison.json
```

Exit 0 means identical raw state; exit 1 means different state. The comparison
records differing byte counts and first addresses per region. It rejects
truncated, unexpected or trailing binary data and refuses to overwrite a report.
`BBVID001` contains the eight ASCII magic bytes, then four regions, each with
little-endian uint32 base/length followed by raw bytes: video I/O at `0x04000000`
(length `0x56`), palette at `0x05000000` (`0x400`), VRAM at `0x06000000`
(`0x18000`) and OAM at `0x07000000` (`0x400`). Total size is 100478 bytes.

These are end-of-capture snapshots, not per-scanline state or a save state. A
whole CPU instruction can cross the nominal capture deadline; use the recorded
cycle, PC and CPSR when investigating differences. Equal raw state does not prove
equal mid-frame register history; LCD status can differ near a boundary even
when completed images match. ROM/BIOS/backup bytes are excluded, but video memory
and generated PNGs can contain game assets and remain outside Git.

## Reference pixel precision

Build the unmodified mGBA 0.10.5 library and capture adapter with matching
pixel types. The helper requires a C11 compiler, CMake, make and Python 3;
capture also requires Pillow. Source and dependency builds stay outside Git.

```bash
bash tools/build-mgba-reference.sh \
  --source /path/to/mgba-0.10.5 \
  --output /path/to/reference-rgb555 \
  --color-mode rgb555 --jobs 4
/path/to/reference-rgb555/mgba-capture --describe
```

Use `--color-mode rgb888` and a separate output directory for the control build.
The default output is `target/mgba-reference/<mode>`. The helper compiles both
the library and adapter with `COLOR_16_BIT` for RGB555, and neither with that
define for RGB888. It verifies the linked mGBA version and records format,
defines and source/library/binary hashes in `reference-build.json`. When using
the retained cloud tools, prepend
`/workspace/toolchains/cmake-python/cmake/data/bin` to PATH for CMake.

Use either binary with `tools/reference_capture.py`; the reader obtains pixel
precision from the stream rather than a caller-supplied label. `BBREF002`
contains two little-endian uint32 values after its eight-byte magic: format and
internal bytes per pixel, either `(0,4)` for RGB888 or `(1,2)` for RGB555.
Frame headers and payloads remain unchanged: RGB888 pixels and stereo PCM16.
RGB555 output expands each finished 5-bit channel using `(v<<3)|(v>>2)`.
There is no quantization of an RGB888 reference or replacement of captured
pixels. Legacy `BBREF001` streams retain their previous RGB888 interpretation.
Unknown/inconsistent format declarations fail; RGB565 adapter builds are
rejected because their channel widths differ from the GBA's.

RGB555 describes storage and arithmetic precision, not a hardware-correctness
claim. In unmodified mGBA 0.10.5, `_darken` divides shifted green/blue fields
before masking them. This rounds differently from applying the operation to
each unshifted 5-bit channel. The observed menu difference therefore remains
open even though BIOS alpha blending now matches. See
[the measured comparison](REFERENCE-VALIDATION.md#rgb555-reference-qualification).

## Bounded guest-event diagnostics

For a direct `ScenarioRunner` configuration, enable LCD callback snapshots with:

```properties
event_trace=true
trace_start_cycle=0
trace_end_cycle=3370753
trace_capacity=65536
trace_events=lcd
```

This example includes the last boundary of a 12-frame, zero-warmup capture.
The window is `[start, end)`, defaults to the complete configured run including
its final boundary, and must remain inside that budget. `trace_events=all`
also records other scheduled callbacks; audio/pixel clocks can fill the buffer
quickly, so narrow the window. The default is LCD only. Capacity is 1..1000000
rows, with a default of 65536. Invalid settings fail before output creation.

`events.tsv` records before/after callback state: effective cycle, dispatch cycle,
phase, local event ID/type, PC, CPSR, VCOUNT, DISPSTAT, DISPCNT, BLDCNT,
BLDALPHA, BLDY, IE, IF, IME and HALT. Appended fields `bg2cnt`, `bg2pa`,
`bg2pb`, `bg2pc`, `bg2pd`, `bg2x` and `bg2y` capture the BG2 affine control,
matrix and reference registers without changing existing column positions.
Numbers are unsigned decimal. Event IDs
identify callback instances within one trace, not devices across emulators.
PC is the CPU's current instruction position during dispatch, not a bus trace.
The optional observer stays on the guest owner, copies primitive values using
read-only peeks, and performs no disk IO. Serialization occurs after detaching.
Only the diagnostic buffer is bounded by this setting; normal capture continues
after it fills. The report explicitly counts `dropped_rows` and marks a truncated
trace. A failed device callback has no successful `after` record.

Recompile `tools/mgba-capture.c`, then pass `--event-trace` and optional
`--trace-start-cycle`, `--trace-end-cycle`, `--trace-capacity` to
`tools/reference_capture.py`. The mGBA adapter observes LCD callbacks only. It
buffers the same columns without changing the event's context, priority or
deadline. `cycle` is its effective deadline (`dispatch_cycle - cyclesLate`);
`dispatch_cycle` exposes instruction-level lateness. BerryBoy dispatches at the
exact scheduler deadline, so its two cycle columns are equal. The normal RGB/PCM
protocol is unchanged; reference metadata also records trace truncation.

These snapshots diagnose scheduled event order. They do not record every CPU
bus transaction, BIOS-protected read, register write or IRQ entry. In particular,
end-of-frame blend coefficients may already belong to the next frame; inspect
the visible-line trace before explaining a pixel difference. A matching trace
does not establish hardware correctness or physical playback performance.
See the [BIOS startup diagnosis](REFERENCE-VALIDATION.md#bios-startup-event-diagnosis)
for measured noninterference and the remaining timing questions.

## Current validation

Two three-frame captures of the original demo produced identical video/PCM
hashes and guest traces, 1645 stereo samples per run, no missing guest frames and
no software audio-buffer failures. One cold-run work deadline was missed; these
smoke runs are not sustained performance evidence. Java regressions also cover
wrong hashes, malformed input ordering, stale output refusal and reference
mismatch. [Eleven uploaded commercial games](GAME-COMPATIBILITY.md) now have
360-frame BIOS captures and 1200-frame scripted-input attempts. After incremental
DMA service and BIOS/open-bus behavior fixes, all eleven 1200-frame reports have
no frame/audio counter failures. Two Metroid Fusion captures produce byte-identical
guest traces, WAV audio and final PNGs. A bus spot check agrees with mGBA;
complete independent video/audio comparison now reports mismatches for all eleven
titles over 3600-frame captures; see [REFERENCE-VALIDATION.md](REFERENCE-VALIDATION.md).
Four save initialization/reload files match mGBA. Physical-device captures remain unrun.


The committed LeafGreen recordings in `benchmarks/inputs/` cover a 6950-frame
fresh-game/manual-save route and a 1272-frame continuation from the same copied
save. The independent restored-room checkpoint matches every pixel; menu and
full-stream hashes still differ. See REFERENCE-VALIDATION.md for asset identities,
source, counters and reproduction requirements.

## CPU checkpoint comparison at equal cycles

`tools/CpuCheckpointProbe.java` replays the fresh-backup regression input and
copies CPU/IRQ state into bounded host records. It loads no save and writes no
save. Set `fresh_backup=true` explicitly in a copy of the original scenario
properties; retain the verified ROM, BIOS and input paths/hashes. This probe
supports default RTC, no peripherals and automatic backup detection only.

The second argument is a file of inclusive `startCycle endCycle` pairs, sorted,
nonoverlapping and inside the 3600-frame regression. Each window spans at most
10000 cycles; the total is bounded to 100000 samples and 256 windows. For the
first Lost Age case, use `90448312 90448712` (frame 322 +/- 200 cycles).

```bash
mkdir -p target/cpu-probe/classes
javac -Xlint:all -Werror -cp target/classes -d target/cpu-probe/classes tools/CpuCheckpointProbe.java
java -cp target/classes:target/cpu-probe/classes CpuCheckpointProbe \
  /path/to/fresh.properties /path/to/windows.tsv > target/cpu-probe/after.csv
```

For the previous DMA model, export only its source to an ignored directory:

```bash
mkdir -p target/cpu-probe/before-source/berryboy/bus target/cpu-probe/before-classes
git show '9f45db8^:src/main/java/berryboy/bus/DmaController.java' \
  > target/cpu-probe/before-source/berryboy/bus/DmaController.java
javac -cp target/classes -d target/cpu-probe/before-classes \
  target/cpu-probe/before-source/berryboy/bus/DmaController.java
java -cp target/cpu-probe/before-classes:target/classes:target/cpu-probe/classes \
  CpuCheckpointProbe /path/to/fresh.properties /path/to/windows.tsv > target/cpu-probe/before.csv
```

All other production classes must remain identical to the phase-correction
revision; otherwise this isolates more than DMA. No checkout, worktree or reset
is required. `clock` rows copy state from a callback at each requested cycle,
which may occur inside an instruction or DMA access. `retire` rows follow a
completed instruction; `step` rows follow other completed CPU steps, including
DMA, HALT and interrupt handling. Registers r0-r14, PC, CPSR, HALT, IF and the
retired instruction count are retained. IF is queried through its raw device
port: a CPU-context memory read would charge cycles and recurse into the clock.

Compare clock rows at equal cycles and completed-step rows at shared cycles.
Compare retire rows by instruction index separately: different loop iteration
counts can invalidate that alignment. Keep unmatched keys and differing fields
explicit. Matching CPU observations do not prove equal memory/peripheral state,
hardware accuracy or full-game equivalence. The asset-free host tests verify
window validation and unchanged completed-step records when sample callbacks
are omitted from a separately compiled control adapter during active CPU
execution. Sampling deadlines subdivide HALT waits, so idle-step records can
change. Omit `machine.clock.schedule(sample, windows.getFirst()[0]);` in a
separately compiled control copy to check retirement-row equality for a game;
do not require identical idle-step counts. This control was run on both DMA
variants for all four titles with differing equal-cycle CPU observations.
The [diagnosis record](../benchmarks/cpu-checkpoint-diagnosis-2026-11-05.json)
contains every window as `[frame,start,end,differentClockRows,differentSharedStepRows]`.
Extract the second/third entries for the selected game's `windows` to construct
its two-column input file. Keep separate files/output paths for each title.

## Retirement prefix and release-boundary probes

Use the same verified `fresh_backup=true` scenario and before-DMA classpath as
the CPU checkpoint comparison. These probes share its validated fresh-machine
loader. Compile all three host tools:

```bash
mkdir -p target/retirement-probe/classes
javac -Xlint:all -Werror -cp target/classes -d target/retirement-probe/classes \
  tools/CpuCheckpointProbe.java tools/CpuRetirementProbe.java tools/DmaHandoffProbe.java
java -cp target/classes:target/retirement-probe/classes CpuRetirementProbe \
  digest /path/to/fresh.properties 206458760 > target/retirement-probe/after.csv
java -cp target/cpu-probe/before-classes:target/classes:target/retirement-probe/classes \
  CpuRetirementProbe digest /path/to/fresh.properties 206458760 > target/retirement-probe/before.csv
```

Each row hashes an independent block of 4096 completed instructions; the final
row may be partial. Each retirement contributes 81 bytes: little-endian cycle
u64, PC/CPSR u32, r0-r14 u32, IF u32 and HALT u8. `cycle` is the last retirement
in that block. A whole CPU step can cross the requested cycle budget. No sample
events or wall-clock timing enter the digest. Find the first differing block,
then expand at most 4096 instruction indices:

```bash
java -cp target/classes:target/retirement-probe/classes CpuRetirementProbe \
  trace /path/to/fresh.properties 51556353 51560448 > target/retirement-probe/after-detail.csv
java -cp target/classes:target/retirement-probe/classes DmaHandoffProbe \
  /path/to/fresh.properties 206401440 206402110 > target/retirement-probe/after-dma.csv
```

Repeat with the old-DMA classpath. The handoff adapter reads private DMA fields
through a host-only reflection adapter and copies state at existing callbacks
and completed CPU steps. It never writes fields, schedules events or reads
through the CPU bus. An incompatible field layout fails explicitly. Its window
is limited to 10000 cycles. Retirement tracing has a 3600-frame cycle safety
limit; reaching it before the requested retirement fails.

For the independent minimal release case, reconfigure/build the pinned NBA core:

```bash
cmake --build target/nba-reference --target nba-dma-release-probe --parallel 4
target/nba-reference/nba-dma-release-probe
```

Expected CSV is `6,18,24,1`: primary ownership, next ownership, total ownership,
FIFO ready after release. NBA FIFO requests at cycle 6 activate at 8; the
BerryBoy regression injects readiness at 8. Compare ownership after readiness,
not absolute request/CPU latency. The reference DMA, bus and scheduler are
unmodified. This single asset-free case supports the release split, not full
hardware or gameplay qualification.

## FIFO activation and CPU probes

Use the pinned, unmodified NBA checkout/CMake configuration from the independent
ownership section. This probe executes the original CPU rather than borrowing
its event slot. It fills the ARM pipeline first, and enters Thumb through a
real BX/refill. Two/five warmup cycles are asserted and excluded from all
reported cycles. No BIOS, game ROM or save is required.

```bash
cmake --build target/nba-reference --target nba-dma-activation-probe --parallel 4
target/nba-reference/nba-dma-activation-probe > target/nba-reference/activation.csv
mkdir -p target/docs-tools
javac -Xlint:all -Werror -cp target/classes -d target/docs-tools tools/DmaActivationProbe.java
java -cp target/classes:target/docs-tools berryboy.bus.DmaActivationProbe > target/nba-reference/activation-berryboy.csv
```

Reconfigure CMake when using an older build directory. Each CSV has 96 rows:
ARM/Thumb, ADD/LDR, three DMA sources, one/two channels and four retirements.
Code/data use IWRAM. `cycle` is relative to the FIFO request after priming;
`pc` is the next instruction address, normalized from NBA's pipeline r15.
Both adapters validate r0 and PC progression. The reference checks complete
FIFO source progress before the first load retires. A CSV mismatch is an
observed model difference, not an adapter process failure or a physical pass.

For CPU internal-cycle arbitration after activation, normalize BerryBoy
readiness to the reference's cycle 2:

```bash
java -cp target/classes:target/docs-tools berryboy.bus.DmaActivationProbe \
  --ready-at-two > target/nba-reference/activation-ready-berryboy.csv
cmp target/nba-reference/activation.csv target/nba-reference/activation-ready-berryboy.csv
```

This mode now matches all 96 reference rows. It does not change production DMA
request timing and must not be interpreted as an activation-delay pass. The
default request-mode comparison remains unmatched. During resumable internal
timing, frame/step snapshots can expose executed-but-unretired registers/PC;
use `Cpu.instructionInFlight()` and retirement counts when interpreting them.

Production timing remains unmatched. The evidence contains an exact patch for
an ignored, host-only delay experiment on the pre-resumption core. On that
revision, adding two cycles to pending scheduling alone fails all twelve
first-load ordering regressions. Reproduce it with the source revision recorded
in that evidence; mixing historical DMA classes with the current CPU's new
ownership-query dependency is unsupported. The internal-cycle stage now
preserves readiness-normalized ordering. Data arbitration is now implemented;
fetch/refill boundaries and actual activation scheduling remain open. Do not install the
old experiment or treat ADD matches as complete CPU/DMA qualification.
See [the comparison and constraints](REFERENCE-VALIDATION.md#fifo-activation-and-cpu-load-ordering-2026-11-05).

## CPU data arbitration probes

Use the same pinned, unmodified NBA source and CMake configuration. These
asset-free adapters execute LDR or two-register LDM in ARM/Thumb, with data in
IWRAM or Game Pak ROM, three DMA source regions and readiness at cycle 1 or 2.

```bash
cmake --build target/nba-reference --target nba-dma-data-probe --parallel 4
target/nba-reference/nba-dma-data-probe > target/nba-reference/data.csv
javac -Xlint:all -Werror -cp target/classes -d target/docs-tools tools/DmaDataProbe.java
java -cp target/classes:target/docs-tools berryboy.bus.DmaDataProbe > target/nba-reference/data-berryboy.csv
cmp target/nba-reference/data.csv target/nba-reference/data-berryboy.csv
```

All 48 rows must match, including cycles, loaded registers, writeback and PC.
NBA's normal two-word DMA3 request uses its original two-cycle activation;
aging that request one cycle puts readiness at the end of the opcode fetch.
BerryBoy explicitly injects raw readiness at the same relative cycle. This
isolates data arbitration and does not qualify production activation timing.
DMA overwrites the IWRAM load target: readiness at 1 changes the first load;
readiness at 2 preserves the completed first read and changes LDM's second.
For ROM data, readiness at 2 occurs during the first eight-cycle read. DMA
between LDM reads forces the next ROM read to be nonsequential (eight rather
than six cycles). These selected observations are model comparison evidence,
not a hardware or full-pipeline qualification.

Use the pinned, unmodified NBA checkout and CMake configuration above:

```bash

```

Reconfigure CMake when using an older build directory. Both probes run without
external assets. The 36 rows execute same-mode BX in ARM/Thumb, two refill
target regions and three two-word DMA3 source regions. `ready=0` means a no-DMA
control, not readiness at cycle zero. For `ready=1/2`, NBA ages its original
two-cycle immediate request; BerryBoy injects raw readiness. Cycles exclude
the asserted NBA priming and optional request age. `pc` is the next instruction
address; `dma_complete` inspects the second destination word at retirement.

All 36 rows now match. The preceding atomic-refill core matched only the 12
no-DMA controls and retired prematurely in all 24 ready cases. This isolates
refill arbitration; it does not qualify actual request activation or full
opcode-pipeline latching. See [the diagnosis](REFERENCE-VALIDATION.md#cpu-branch-refill-dma-counterexample-2026-11-05)
and [the correction](REFERENCE-VALIDATION.md#resumable-cpu-pipeline-refills-during-dma-2026-11-05).

```bash
cmake --build target/nba-reference --target nba-cpu-refill-forms-probe --parallel 4
```

unit tests separately check suspended entry without handler execution. PC,

## Opcode-fetch handoff and IRQ probes

Use the same pinned, unmodified NBA source/CMake setup:

